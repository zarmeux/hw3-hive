# ДЗ №3 — Apache Hive: развёртывание

В этом ДЗ мы настроили Hive так, чтобы с ним могли одновременно работать несколько клиентов. Metastore вынесли в отдельный сервис, метаданные храним в PostgreSQL, а сами данные — в HDFS. Ещё мы сделали таблицу с партициями по датам и скрипт загрузки, который можно запускать повторно без дублей.

Репозиторий: https://github.com/zarmeux/hw3-hive

## Быстрый запуск

Мы ставим Hive на управляющей машине уже работающего кластера Hadoop. Для запуска нужны Java 11, настройки кластера в `/etc/hadoop-yarn` и пользователь `hadoop` с административным доступом к HDFS.

```bash
git clone https://github.com/zarmeux/hw3-hive.git
cd hw3-hive
mkdir -p evidence
set -o pipefail
sudo bash scripts/install.sh 2>&1 | tee evidence/install.log
sudo bash scripts/demo.sh 2>&1 | tee evidence/demo.log
```

Дальше мы используем каталог `~/hw3-hive`. HDFS и YARN у нас остались с предыдущих работ, заново их здесь не устанавливаем. Если запускать проект на другом кластере, в `/etc/hadoop-yarn` должны лежать его настройки. Ещё понадобятся `sudo`, доступ к репозиториям Ubuntu и архиву Apache, примерно 2 ГБ свободного места и 2 ГБ доступной памяти.

## На чём мы запускали

- Управляющая машина: Ubuntu 24.04, 4 ГБ RAM.
- OpenJDK 11 и Hadoop 3.4.2 в `/opt/hadoop`.
- Настройки кластера в `/etc/hadoop-yarn`.
- Адрес NameNode из `core-site.xml`, адрес ResourceManager из `yarn-site.xml`. Мы проверяли работу с тремя рабочими узлами.
- Hive `4.0.0-alpha-2` из официального архива Apache. При установке мы проверяем SHA256.
- PostgreSQL из репозитория Ubuntu и JDBC-драйвер из `libpostgresql-jdbc-java`.

Для запросов мы используем уже настроенный MapReduce/YARN. При проверке выяснилось, что контейнерам не хватает `commons-collections-3.2.2.jar`. Поэтому мы передаём эту библиотеку из комплекта Hive через `hive.aux.jars.path`.

Для временных файлов заданий мы выделили `/user/hive/staging` через `yarn.app.mapreduce.am.staging-dir`. Иначе Hive пытался писать в закрытый каталог пользователя `yarn` и получал ошибку доступа.

## Как всё устроено

```text
Beeline client 1 ─┐
                 ├─ HiveServer2 (127.0.0.1:10000)
Beeline client 2 ─┘          │
                            ├─ отдельный Metastore (127.0.0.1:9083)
                            │           └─ PostgreSQL / hive_metastore
                            └─ существующие HDFS и YARN
```

Мы запускаем Metastore и HiveServer2 отдельными процессами от пользователя `hive`. Адрес Metastore задаём в `hive.metastore.uris`, embedded Derby здесь нет. В PostgreSQL лежат метаданные, а файлы таблиц — в HDFS. Используем каталоги `/user/hive/warehouse`, `/user/hive/warehouse-external` и `/tmp/hive`.

Для служебных уведомлений Metastore мы добавили `hadoop.proxyuser.hive.hosts=127.0.0.1` и `hadoop.proxyuser.hive.groups=hive` в `/etc/hive/hadoop/core-site.xml`. Это отдельная копия настроек Hadoop для Hive, её мы подключаем через `HADOOP_CONF_DIR=/etc/hive/hadoop`. Исходные настройки кластера не меняем. Так правила доступа подхватываются ещё при инициализации ProxyUsers в Hadoop 3.4.2, при этом сама проверка доступа остаётся включённой.

Порты Hive мы оставили на `127.0.0.1`, с компьютера подключаемся через SSH-туннель. В учебном примере стоят `authentication=NONE` и `doAs=false`, поэтому запросы обоих клиентов выполняются от пользователя `hive`. Отдельные права для каждого клиента мы здесь не настраивали.

## Установка

На управляющей машине запускаем установочный скрипт:

```bash
cd ~/hw3-hive
mkdir -p evidence
set -o pipefail
sudo bash scripts/install.sh 2>&1 | tee evidence/install.log
```

В `install.sh` мы собрали весь порядок установки: скачивание и проверку Hive, установку PostgreSQL, создание пользователя и настроек, подготовку БД Metastore и каталогов HDFS. Затем скрипт создаёт службы systemd, ждёт готовности портов и проверяет запросы через Beeline. Настройки существующего Hadoop он не меняет.

Пароль БД мы генерируем на сервере и сохраняем в `/etc/hive/metastore.password` с правами `0600`. Он также попадает в `/etc/hive/hivemetastore-site.xml`, который доступен root и группе hive. Эти файлы в репозиторий не добавляем.

При повторном запуске скрипт сохраняет прежний пароль. Если БД уже не пустая, но схема в ней повреждена или не подходит, нужно сначала разобраться с ошибкой вручную. Уже работающие службы после изменения настроек скрипт автоматически не перезапускает.

## Как мы проверяем подключение

```bash
cd ~/hw3-hive
sudo -u hive bash scripts/check.sh 2>&1 | tee evidence/check.log
sudo systemctl status hive-metastore hive-hiveserver2 --no-pager
sudo ss -lntp | grep -E ':(9083|10000|10002)\b'
```

В `check.sh` мы одновременно запускаем два клиента Beeline. Оба должны выполнить `SHOW DATABASES` и `SELECT 1` без ошибок. Так мы проверяем работу нескольких подключений, но большую нагрузку этим тестом не моделируем.

Если что-то не запустилось, смотрим `/var/log/hive/metastore.log`, `/var/log/hive/hiveserver2.log` и `/var/log/hive/hive.log`. Ещё можно посмотреть службы через `journalctl -u hive-metastore -u hive-hiveserver2`.

## Подключение с компьютера

Сначала открываем SSH-туннель. Вместо `USER@SSH_HOST` указываем своего пользователя и адрес управляющей машины:

```bash
ssh -N -L 10000:127.0.0.1:10000 USER@SSH_HOST
```

В другом терминале запускаем Beeline, он должен быть установлен на компьютере:

```bash
beeline -u jdbc:hive2://127.0.0.1:10000/default -n hive
```

Можно работать и прямо на сервере. В этом случае мы запускаем Beeline через `sudo -u hive` с переменными окружения из `scripts/check.sh`.

## Таблица и загрузка данных

Для примера мы взяли события пользователей и создали внешнюю таблицу `hw3.events` в формате TEXTFILE. В ней три обычные колонки: `event_id BIGINT`, `user_id BIGINT`, `event_type STRING` и партиция `event_date STRING`. SQL лежит в `sql/create-events.sql`, а файлы данных — в `/user/hive/warehouse-external/hw3/events/event_date=YYYY-MM-DD/`.

Создаём базу и таблицу, потом загружаем наши два файла:

```bash
cd ~/hw3-hive
sudo bash scripts/create-table.sh
sudo bash scripts/load-partition.sh data/events-2026-10-20.csv 2026-10-20
sudo bash scripts/load-partition.sh data/events-2026-10-21.csv 2026-10-21
sudo bash scripts/run-sql.sh sql/inspect-events.sql
```

Мы используем простой CSV без заголовка: три значения в строке, например `1,101,page_view`. Идентификаторы должны быть неотрицательными BIGINT. Тип события начинается с латинской буквы, дальше можно использовать латинские буквы, цифры и подчёркивания. Кавычки, запятые внутри поля и пустые файлы мы в этом примере не поддерживаем. Дату передаём отдельным аргументом, в самом CSV её нет.

В `load-partition.sh` мы сначала проверяем дату и содержимое CSV. Затем копируем файл во временный каталог HDFS и через HiveServer2 выполняем `LOAD DATA INPATH ... OVERWRITE INTO TABLE hw3.events PARTITION (event_date='...')`. Hive сам регистрирует партицию. После загрузки мы убираем временные файлы, исходный CSV остаётся на месте. Если запустить этот скрипт дважды для одной даты на управляющей машине, локальная блокировка заставит второй запуск дождаться первого.

Мы выбрали загрузку с перезаписью: **скрипт заменяет всё содержимое выбранной партиции**. Поэтому в файле должен быть полный набор событий за эту дату. Остальные даты не меняются, а повторный запуск с тем же файлом не добавляет дубли. Транзакции для одновременного чтения и загрузок из других программ мы здесь не реализовывали.

Чтобы проверить повторный запуск, ещё раз загружаем первую дату:

```bash
sudo bash scripts/load-partition.sh data/events-2026-10-20.csv 2026-10-20
sudo bash scripts/run-sql.sh sql/inspect-events.sql
```

После этого у нас должны остаться две партиции: 3 строки за `2026-10-20` и 2 за `2026-10-21`, всего 5 строк.

Через `scripts/run-sql.sh` мы можем выполнить свой локальный SQL-файл в Beeline от пользователя `hive`. В создании таблицы стоит `IF NOT EXISTS`, поэтому повторный запуск её не пересоздаёт. Если нужно поменять схему уже созданной таблицы, это делаем отдельно.

Синтаксис `LOAD DATA` мы брали из [документации Hive DML](https://hive.apache.org/docs/latest/language/languagemanual-dml/).

## Проверка запроса через YARN

Для проверки распределённого выполнения мы запускаем:

```bash
sudo bash scripts/check-yarn.sh
```

В `sql/check-yarn.sql` мы считаем события по датам через `COUNT(*)`. Для этого запроса отключаем FetchTask и получение ответа из статистики, выбираем движок `mr`. Так запрос действительно проходит через MapReduce.

Скрипт проверяет, что получили `3` и `2`, что работали mapper и reducer, а приложение YARN имеет тип `MAPREDUCE` и итоговый статус `SUCCEEDED`. Логи записываем в `evidence/yarn-query.log` и `evidence/yarn-application.log`.

Чтобы после установки повторить весь наш пример одной командой:

```bash
sudo bash scripts/demo.sh
```

В `demo.sh` мы собрали создание таблицы, загрузку двух дат, повторную загрузку первой, проверку двух клиентов и запрос через YARN. При запуске он перезапишет обе партиции с примером данных. Мы проверяли небольшой набор событий, нагрузочные тесты не проводили.

### Проверка полного сценария и YARN

Мы запустили `sudo bash scripts/demo.sh` целиком и получили код `0`. После повторной загрузки в партициях осталось 3 и 2 события, оба клиента Beeline выполнили свои запросы. Запрос через YARN тоже прошёл: тип приложения `MAPREDUCE`, один mapper и один reducer, `Final-State: SUCCEEDED`. Получили `2026-10-20: 3` и `2026-10-21: 2`.

Подробные логи `scripts/demo.sh` и `scripts/check-yarn.sh` мы сохраняем на сервере. В публичный репозиторий их не выкладываем, там могут быть адреса и имена узлов.
